# Upgrading to EQL 2.4

`2.4.x` introduces the encrypted-domain scalar type family (`eql_v2_<T>`, `eql_v2_<T>_eq`, `eql_v2_<T>_ord`, `eql_v2_<T>_ord_ore`) and a small set of behaviour changes on the legacy `eql_v2_encrypted` composite type. The `eql_v2` schema name, the composite-type name, and the wire payload format are unchanged.

## TL;DR

1. **MIN / MAX moved to the encrypted-domain family** ([U-009](#u-009-min--max-moved-to-per-domain-aggregates)). `eql_v2.min(eql_v2_encrypted)` / `eql_v2.max(eql_v2_encrypted)` no longer exist. Either re-type the column as `eql_v2_<T>_ord` (recommended), or cast at the call site.

## Compatibility

| Component | Status |
| --- | --- |
| `eql_v2` schema name | **Unchanged.** |
| `eql_v2_encrypted` composite type | **Unchanged at the storage level.** Columns keep working for `=`, `<>`, `<`, `<=`, `>`, `>=`, `LIKE`, `ILIKE`, `@>`, `<@`, `->`, `->>`, and native `COUNT` / `GROUP BY`. |
| `eql_v2.min(eql_v2_encrypted)` / `eql_v2.max(eql_v2_encrypted)` aggregates | **Removed.** See U-009. |
| `eql_v2_<T>_ord` / `eql_v2_<T>_ord_ore` MIN / MAX aggregates | **New.** Defined per ord-capable variant via the scalar codegen. |
| Native `COUNT(col)` / `COUNT(DISTINCT extractor(col))` / `GROUP BY` on encrypted columns | **Unchanged.** Works on both the legacy type and the new domain family. |
| `SUM` / `AVG` / arithmetic aggregates | **Not supported** on encrypted columns (would require homomorphic encryption). Decrypt at the application boundary. |
| Postgres 14, 15, 16, 17 | Supported. |
| Supabase / managed Postgres | Supported. The ORE operator class is excluded from the Supabase build, so ordered domain columns fall back to seq-scan for range queries — this matches the v2.3 behaviour on `eql_v2_encrypted`. |

## Upgrade notes

### U-009: MIN / MAX moved to per-domain aggregates

**Symptom.** A query that worked in v2.3:

```sql
SELECT eql_v2.min(price_enc) FROM orders GROUP BY customer_id;
```

now fails:

```text
ERROR:  function eql_v2.min(eql_v2_encrypted) does not exist
HINT:   No function matches the given name and argument types. You might need to add explicit type casts.
```

The legacy `eql_v2.min(eql_v2_encrypted)` and `eql_v2.max(eql_v2_encrypted)` aggregates have been removed. The replacement is per ord-capable variant of the encrypted-domain family — `eql_v2.min(eql_v2_<T>_ord)`, `eql_v2.max(eql_v2_<T>_ord_ore)`, etc.

**Why.** The `eql_v2_encrypted` composite type is deprecated in favour of the per-scalar domain family, which encodes search capabilities into the type itself rather than relying on a runtime payload-shape check. The aggregates would have been ambiguous on the composite type (which scalar do you order by?); on the domain types the variant identifies the scalar and the comparator unambiguously.

**Fix.** Choose one of two recipes:

1. **Recommended — re-type the column** to the matching `_ord` variant. Idempotent migration:

   ```sql
   ALTER TABLE orders
     ALTER COLUMN price_enc TYPE eql_v2_int4_ord
     USING price_enc::eql_v2_int4_ord;

   -- Query is then unchanged
   SELECT eql_v2.min(price_enc) FROM orders GROUP BY customer_id;
   ```

   The cast is a metadata-only check against the domain `CHECK` constraint — the underlying jsonb is unchanged. PostgreSQL takes an `ACCESS EXCLUSIVE` lock on the table for the duration; on a hot table run during a maintenance window.

2. **Lower-friction — cast at the call site** without changing the column type:

   ```sql
   SELECT eql_v2.min(price_enc::eql_v2_int4_ord) FROM orders GROUP BY customer_id;
   ```

   This works for any one-off query but every call site needs the cast.

**`Eq`-only columns.** If your column was typed `eql_v2_<T>_eq` (HMAC-only), MIN / MAX has no meaningful semantics — equality terms don't reveal order. Re-type to `eql_v2_<T>_ord` (or `_ord_ore`) if you need ordering, which requires the payload to carry the `ob` (ORE block) term. The proxy will populate this term on insert; existing rows must be re-encrypted.

**Rollback.** Re-installing the previous EQL release reinstates the legacy aggregates. The replacement per-domain aggregates are additive — installing v2.4 over a v2.3 database where `eql_v2_encrypted` columns exist does not break the columns themselves, only their use with MIN / MAX through the removed names.

**Verification checklist.**

- [ ] `grep -rn 'eql_v2\.min(\|eql_v2\.max(' .` over your application code — every match should pass a domain-typed expression (column already typed as `eql_v2_<T>_ord` / `_ord_ore`, or a cast at the call site).
- [ ] `EXPLAIN` an updated aggregate query — the plan should show the aggregate routing through the variant's own `<` / `>` operator. The ORE comparator runs on each pairwise compare; index engagement (functional ORE btree on `eql_v2.ord_term(col)`) speeds up filter predicates but not the aggregate's pairwise scan.
- [ ] `SELECT eql_v2.min(NULL::eql_v2_int4_ord) FROM generate_series(1, 3)` returns `NULL` (smoke test for the STRICT state function — all-NULL input).
