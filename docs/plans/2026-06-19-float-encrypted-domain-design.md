# Design: `float4` / `float8` encrypted-domain types

Date: 2026-06-19
Status: Approved (pending spec review)
Scope: Add IEEE-754 binary-float encrypted-domain coverage (`real` / `double precision`) to the `eql_v3` scalar surface.

## Problem

EQL v2's cast allowlist (`src/config/functions.sql:50`) accepts `real`, `double`,
and `float` — IEEE-754 binary floats. The v3 catalog (`eql-scalars::CATALOG`) has
no float domain; the only numeric option is `numeric` (arbitrary-precision,
`rust_decimal::Decimal`). So a v2 column declared `real`/`double` has **no direct
v3 equivalent**. This closes that gap by adding `float4` and `float8` as ordered
encrypted-domain scalar types.

## Key crypto facts (verified)

These facts (from `orderable-bytes-0.1.1/src/primitive.rs`,
`cipherstash-client-0.35.0/src/encryption/ore_indexer/mod.rs`, and
`tests/sqlx/src/fixtures/cipherstash.rs`) drive the entire design:

1. **Single f64 crypto path.** cipherstash has exactly one float plaintext,
   `Plaintext::Float(Option<f64>)`. The `real`, `double`, and `float` casts **all**
   map to `ColumnType::Float` (f64) in `cast_to_column_type`. There is no f32
   crypto path — a `real` is widened to f64 before encryption. So `float4` vs
   `float8` is purely a Postgres-surface distinction (column type, domain name,
   decrypt type); the ciphertext and ORE term are byte-identical f64.

2. **f64 ORE order is correct for all non-NaN values.** The `ToOrderableBytes for
   f64` impl applies the standard monotonic IEEE-754 mapping. `f64::ENCODED_LEN ==
   8` (same as `i64`), so the already-generalized N-block ORE comparator orders
   floats with no comparator change. Proven by the upstream
   `f64_byte_order_matches_natural_order` test, which spans `NEG_INFINITY … MIN …
   -1.0 … 0.0 … 1.0 … MAX … INFINITY` and subnormals.

3. **`-0.0` canonicalizes to `+0.0`** (byte-equal), matching IEEE `-0.0 == 0.0`.

4. **NaN is explicitly unspecified.** Different NaN bit patterns produce different
   bytes, and NaN is unordered. The encoder's order/equality guarantees apply only
   to non-NaN inputs. The v3 SQL domain only ever sees ciphertext, so it **cannot**
   inspect or reject a NaN plaintext — any NaN rejection would have to live
   client-side (out of this repo's scope).

## Architecture

`float4`/`float8` are **ordered scalars** using the existing four-domain shape
`ORDERED_INT_DOMAINS` (storage `""`, `_eq` `[Hm]`, `_ord_ore` `[Ore]`, `_ord`
`[Ore]`). The closest existing analogue is `numeric` — a non-integer,
value-owning, string-backed-fixture ordered scalar that introduced the "fourth
fixture shape" (touches the proc-macro routing, not just the type list). Float is
the same shape, duplicated across two widths plus a new `ScalarKind`.

No new comparator, no new domain shape, no new operators. The SQL surface is
generated by the existing kind-agnostic renderers.

### Decision record (resolved)

- **NaN — excluded from fixtures.** Unordered and unspecified in the encoder;
  Rust/Postgres/ORE disagree on its ordering. Mirrors `text` excluding the empty
  string (#262). Behaviour is instead *captured* by a dedicated regression suite
  (see Testing → `float_special`).
- **`-0.0` — excluded; only `+0.0` is a fixture.** The encoder canonicalizes
  `-0.0 → +0.0`, so including both would duplicate a fixture row and break
  `fetch_fixture_payload`'s `fetch_one`.
- **`±Inf` — included**, as the `min_pivot` / `max_pivot` boundary anchors. They
  order correctly across Rust, Postgres, and ORE.
- **Two widths, one crypto path.** Both encrypt via `Plaintext::Float(Some(x as
  f64))`. `float4` fixtures use only values exactly representable in f32 (e.g.
  `0.5`, `-2.25`, powers of two) so the `real` round-trip is lossless; f32→f64
  widening is exact and monotonic, so the oracle holds.
- **Cast tokens — distinct per width** for surface faithfulness even though the
  ciphertext is identical f64: `float4` → `Cast::REAL` (plaintext column `real`),
  `float8` → `Cast::DOUBLE` (plaintext column `double precision`). Both resolve to
  `ColumnType::Float` in `cast_to_column_type`. The bare `float` cast is
  interchangeable with `double` and routes to `float8`. (Supersedes an earlier
  note that both would share `Cast::FLOAT`.)
- **Total order.** `ScalarType` requires `Ord`, which `f32`/`f64` lack. Add thin
  harness newtypes `F4(f32)` / `F8(f64)` implementing `Ord` via `total_cmp` (safe —
  NaN is never stored), `Display`, `Default = 0.0`, and `#[sqlx(transparent)]`
  delegating `Type`/`Decode` to the inner primitive. Avoids an `ordered-float`
  dependency.
- **`SignedScalar` — yes**, origin `0.0` (diverging from `numeric`, which opted
  out), because the signed-zero boundary is a genuine float-specific risk worth
  running through the sign-boundary suite (`encrypted_domain/signed.rs`).

## Test coverage

### Inherited matrix coverage (automatic, catalog-driven)

Once wired, `float4`/`float8` inherit the full ordered-scalar matrix uniformly,
identical to `int4`/`int8`/`date`/`timestamptz`/`numeric`:

- `scalar_matrix!` with `caps = [eq, ord]` (auto-derived from the ordered
  domains): sanity, correctness across all six operators, cross-shape/commuted,
  supported-NULL, blocker raises, index engagement, ORDER BY, ORDER BY USING, ORE
  injectivity (distinct plaintext → distinct ORE blocks).
- All three oracle tiers: catalog (pure Rust), fixture (oracle over committed
  ciphertext), e2e (oracle over fresh encryption).
- The `SignedScalar` sign-boundary suite.
- The matrix-inventory snapshot enforces float emits the same test-name set as
  every other ordered scalar — coverage parity is CI-gated, not optional.

`±Inf` is covered by the generic oracle (they are fixtures/pivots, exercised
through the real DB+crypto path).

### Captured edge-case behaviour (`float_special`, new)

A hand-written behavioural suite `tests/sqlx/tests/encrypted_domain/float_special.rs`,
registered via `#[path]` mod **outside** `scalars::` (same pattern as
`text_match` / `text_smoke`, so it does not pollute the matrix-inventory
snapshot). Creds-gated / e2e-style — encrypts the special values fresh through
cipherstash at test time, so NaN never enters the shared float8 fixture table
(where it would corrupt the all-pairs oracle). It pins:

- **NaN**: encrypting `f64::NAN` succeeds (no panic) and produces a structurally
  valid `eql_v3.float8` payload that passes the domain CHECK. Because the index
  terms (`hm`, `ore`) are deterministic functions of plaintext+key, two
  encryptions of the **same** NaN bit pattern compare equal under `=` and sort to
  a fixed ORE position — captured and asserted with explicit comments that this is
  an **artifact of the canonical bit pattern, not a supported guarantee**, and
  diverges from IEEE (`NaN != NaN`). Exact eq/order outcomes are confirmed when the
  test is first run (the test discovers-and-locks them).
- **`-0.0` vs `+0.0`**: compare equal and share one ORE block (the
  canonicalization).
- **`±Inf`**: redundant spot-check of the boundary ordering.

Plus cheap Rust unit guards in `eql-scalars` asserting NaN / `-0.0` are not in the
fixture lists.

## Risks / open verification

- **Codegen renderers are assumed kind-agnostic** for ordered scalars but have not
  been audited for a kind switch. First implementation step: add the catalog rows,
  run `cargo run -p eql-codegen`, and confirm `float4`/`float8` SQL generates
  cleanly (ORE width = 8). If a renderer switches on kind, add the small arm.
- **`#[sqlx(transparent)]` on `F4`/`F8`** for `Type` + `Decode` against Postgres
  `real`/`double precision` — confirm the derive covers both; fall back to manual
  impls if not.
- **`float_special` exact eq/order outcomes** are discovered-and-locked on first
  run, not pre-asserted.
