**`public.text_search` is now backed by CLLW-OPE (`op`) instead of block-ORE (`ob`), and the block-ORE shape lives on the new `public.text_search_ore`.** The combined search domain — equality, ordering, and bloom containment in one type — now requires `hm` + `op` + `bf` and orders via `eql_v3.ord_term(col)` returning `eql_v3_internal.ope_cllw`. Its equality (`hm` / `eql_v3.eq_term`) and containment (`bf` / `eql_v3.match_term`) terms are unchanged, and the two domains expose an identical operator surface (`=` `<>` `<` `<=` `>` `>=` `@>` `<@`). This completes the move begun for the `_ord` domains: `ope_cllw` is a domain over `bytea`, so an ordered functional index binds `bytea_ops`, the base type's default operator class. Block-ORE's opclass is hand-written for a composite type and installed by a `DO` block that silently skips on `insufficient_privilege`, so on Supabase and other managed PostgreSQL an ordered index over `text_search` previously *succeeded* at `CREATE INDEX` — binding `record_ops` — and then never engaged. The swap is not about operator capability (OPE's operators were already covered via `Ore`); it removes a silent failure mode. Three consequences for callers: rows in a `text_search` column must carry `op` rather than `ob` (so existing ordered indexes must be rebuilt), `eql_v3.ord_term_ore(public.text_search)` no longer exists — use `eql_v3.ord_term`, or retype the column to `public.text_search_ore` for the zero-re-encryption path — and `public.text_search` now **accepts** the empty string, sorting it first, because OPE encrypts `""` to a well-formed one-byte term while block-ORE produces an unorderable empty array (`ob: []`) that `text_search_ore` still rejects. See [U-006](https://github.com/cipherstash/encrypt-query-language/blob/main/docs/upgrading/v3.0.md#u-006-text_search-is-backed-by-cllw-ope).
