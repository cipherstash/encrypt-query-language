**Selector-with-constraint queries on encrypted JSON are now expressible in natural operator form and functional-index accelerated.** New cross-type comparison operators bind an extracted `public.eql_v3_json_entry` leaf to the per-type query operands carrying the deterministic CLLW-OPE `op` term — `eql_v3.query_<T>_ord` and its explicit twin `eql_v3.query_<T>_ord_ope` — across every ordered family (`integer`, `bigint`, `smallint`, `date`, `timestamp`, `numeric`, `real`, `double`, `text`), in both directions. So `encrypted_json -> 'age_selector'::text > $1::eql_v3.query_integer_ord` matches a functional btree on `eql_v3.ord_term(encrypted_json -> 'selector'::text)` instead of requiring a whole-`public.eql_v3_json_entry` needle or falling back to the explicit function form (seq scan). Every supported operator is backed by a public `eql_v3.*` wrapper, so platforms without operator support can call it by name.

**Ordering is available on every family; equality only where the leaf encoding is lossless.** A JSON leaf is encoded as an f64 (numbers) or a collated string (text), and neither preserves every type. `integer`/`smallint` (every value in range is an exact f64), `real`/`double` (the leaf *is* an f64), and `date`/`timestamp` (ISO-8601 passes through collation unchanged) get all six comparisons. `bigint` (values above 2^53 round — `9007199254740993` and `9007199254740992` share one term), `numeric` (more precision than an f64 carries), and `text` (`"café"` and `"cafe"`, `"user@exämple.com"` and `"user@example.com"` share one term) get ordering only; their `=`/`<>` raise `operator is not supported`. Those operators are absent because an equality built on those encodings returns rows whose plaintext **differs** — a wrong answer, not a missing feature. Scalar columns are unaffected throughout: their equality routes through the exact `hm` term, which a SteVec leaf does not carry. To match a `text`, `bigint`, or `numeric` field exactly, use document containment (`@>`), whose `hm` terms are exact.

Operands whose terms an extracted leaf cannot produce are not bound: `eql_v3.query_<T>_eq` (a JSON scalar leaf carries only `op`, never a per-value `hm`, so an equality binding could never match), `query_<T>_ord_ore` / `query_text_search_ore` (block-ORE), `query_text_match` (Bloom), and `eql_v3.query_text_search` — SteVec has no match/bloom capability, so `search` offers nothing over `_ord` while its CHECK demands an inert `bf`.

The operand must be encrypted for the same **column**, and as the same JSON scalar **type**, as the leaf. Field scoping comes from the `->` extraction, not the operand — an `op` term encodes the plaintext and the column and carries no selector — so a mismatched column or type produces non-corresponding terms and silently returns zero rows; enforcing this is the client's / CipherStash Proxy's responsibility. Existing behaviour is unchanged: `eql_v3.eq_term(public.eql_v3_json_entry)`, document containment, and the entry-to-entry `=` / `<>` / range operators are untouched.
