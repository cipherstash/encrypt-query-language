**Selector-with-constraint queries on encrypted JSON are now expressible in natural operator form and functional-index accelerated.** New cross-type comparison operators bind an extracted `public.eql_v3_json_entry` leaf to the per-type query operands `eql_v3.query_<T>_ord` (the OPE-backed default ordering operand) and its explicit twin `eql_v3.query_<T>_ord_ope`, for every ordered numeric / date family. So `col -> '$.age' > $1::eql_v3.query_integer_ord` — and, because the deterministic CLLW-OPE `op` term serves equality as well as ordering, `col -> '$.age' = $1::eql_v3.query_integer_ord` — matches a functional btree on `eql_v3.ord_term(col -> 'selector'::text)` instead of requiring a whole-`public.eql_v3_json_entry` needle. All six operators (`=`, `<>`, `<`, `<=`, `>`, `>=`) are bound for the numeric / date families; `text` binds only the four range operators (a SteVec string leaf carries no HMAC equality term, so text equality is not available in this operator form). No `eql_v3.query_<T>_eq` operator is bound to `public.eql_v3_json_entry` for any type: a JSON scalar leaf has no per-value equality (`hm`) term, so equality is served exclusively by the `op`-based `query_<T>_ord` path. The operand must be encrypted in the leaf's per-selector field context — an operand encrypted out of that context (a plain scalar, or one for a different selector) silently returns zero rows; enforcing this is the client's / CipherStash Proxy's responsibility. `eql_v3.eq_term(public.eql_v3_json_entry)` and the entry-to-entry `=` / `<>` / range operators are unchanged.
