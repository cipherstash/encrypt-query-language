**Selector-with-constraint queries on encrypted JSON are now expressible in natural operator form and functional-index accelerated.** New cross-type comparison operators bind an extracted `public.eql_v3_json_entry` leaf to the per-type query operands `eql_v3.query_<T>_ord` (the OPE-backed default ordering operand) and its explicit twin `eql_v3.query_<T>_ord_ope`, for every ordered family (`integer`, `bigint`, `smallint`, `date`, `timestamp`, `numeric`, `real`, `double`, `text`). All six comparisons (`=`, `<>`, `<`, `<=`, `>`, `>=`) are bound in both directions, so `encrypted_json -> 'age_selector'::text > $1::eql_v3.query_integer_ord` — and, because the deterministic CLLW-OPE `op` term serves equality as well as ordering, `encrypted_json -> 'email_selector'::text = $1::eql_v3.query_text_ord` — matches a functional btree on `eql_v3.ord_term(encrypted_json -> 'selector'::text)` instead of requiring a whole-`public.eql_v3_json_entry` needle or falling back to the explicit function form (seq scan). Every operator is backed by a public `eql_v3.*` wrapper, so platforms without operator support can call it by name. No `eql_v3.query_<T>_eq` operator is bound to `public.eql_v3_json_entry`: a JSON scalar leaf carries only the `op` term, never a per-value equality (`hm`) term, so equality runs exclusively through the `op`-based `query_<T>_ord` path. The operand must be encrypted in the leaf's per-selector field context — an operand encrypted out of that context (a plain scalar, or one for a different selector) silently returns zero rows; enforcing this is the client's / CipherStash Proxy's responsibility. Existing behaviour is unchanged: `eql_v3.eq_term(public.eql_v3_json_entry)`, document containment, and the entry-to-entry `=` / `<>` / range operators are untouched.
