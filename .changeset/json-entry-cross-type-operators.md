'@cipherstash/eql': patch

**Selector-with-constraint queries on encrypted JSON are now expressible in natural operator form and functional-index accelerated.** New cross-type comparison operators bind an extracted `public.eql_v3_json_entry` leaf to every per-type query operand carrying the deterministic CLLW-OPE `op` term — `eql_v3.query_<T>_ord`, its explicit twin `eql_v3.query_<T>_ord_ope`, and (for `text`) `eql_v3.query_text_search` — across every ordered family (`integer`, `bigint`, `smallint`, `date`, `timestamp`, `numeric`, `real`, `double`, `text`). All six comparisons (`=`, `<>`, `<`, `<=`, `>`, `>=`) are bound in both directions, so `encrypted_json -> 'age_selector'::text > $1::eql_v3.query_integer_ord` — and, because the deterministic CLLW-OPE `op` term serves equality as well as ordering, `encrypted_json -> 'email_selector'::text = $1::eql_v3.query_text_ord` — matches a functional btree on `eql_v3.ord_term(encrypted_json -> 'selector'::text)` instead of requiring a whole-`public.eql_v3_json_entry` needle or falling back to the explicit function form (seq scan). Every operator is backed by a public `eql_v3.*` wrapper, so platforms without operator support can call it by name. Operands whose terms an extracted leaf cannot produce are not bound: `eql_v3.query_<T>_eq` (a JSON scalar leaf carries only `op`, never a per-value `hm`, so an equality binding could never match), `query_<T>_ord_ore` / `query_text_search_ore` (block-ORE), and `query_text_match` (Bloom) — and Bloom's `@@` is never emitted, since a leaf has no `match_term`. The operand must be encrypted in the leaf's per-selector field context — an operand encrypted out of that context (a plain scalar, or one for a different selector) silently returns zero rows; enforcing this is the client's / CipherStash Proxy's responsibility. Existing behaviour is unchanged: `eql_v3.eq_term(public.eql_v3_json_entry)`, document containment, and the entry-to-entry `=` / `<>` / range operators are untouched.
